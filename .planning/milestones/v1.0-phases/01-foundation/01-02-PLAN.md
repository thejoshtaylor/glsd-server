Create all Docker and configuration files:

**backend/Dockerfile** — based on `python:3.12-slim` (NOT `tiangolo/uvicorn-gunicorn-fastapi`):
```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN chmod +x entrypoint.sh

ENTRYPOINT ["./entrypoint.sh"]
CMD ["gunicorn", "app.main:app", "--workers", "1", "--worker-class", "uvicorn.workers.UvicornWorker", "--bind", "0.0.0.0:8000", "--timeout", "120"]
```

**backend/entrypoint.sh** — runs migrations then exec's the CMD:
```bash
#!/bin/bash
set -e

echo "Running database migrations..."
alembic upgrade head

echo "Starting application server..."
exec "$@"
```
The `exec "$@"` pattern replaces the shell with gunicorn so Docker SIGTERM goes to the app process.

**docker-compose.yml** — two services (api + db), single-worker enforced (per DEPLOY-01, DEPLOY-02):
```yaml
services:
  api:
    build: ./backend
    command: >
      gunicorn app.main:app
      --workers 1
      --worker-class uvicorn.workers.UvicornWorker
      --bind 0.0.0.0:8000
      --timeout 120
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "8000:8000"

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-glsd}
      POSTGRES_USER: ${POSTGRES_USER:-glsd}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-glsd_password}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-glsd} -d ${POSTGRES_DB:-glsd}"]
      interval: 5s
      timeout: 5s
      retries: 5
    ports:
      - "5432:5432"

volumes:
  postgres_data:
```
Key points: `--workers 1` in both Dockerfile CMD and compose command (belt-and-suspenders). `depends_on` with `condition: service_healthy` prevents migration race. DB ports exposed for local development tooling.

**Step 2: Generate the initial migration.**
Because Alembic autogenerate requires a running database, and we want to avoid that complexity during initial setup, create the migration file manually based on the models. The migration file `backend/alembic/versions/0001_initial_schema.py` should:

- Revision ID: use a short hex string (e.g., `"0001"` or generate one)
- `revision = "0001"`
- `down_revision = None`
- `branch_labels = None`
- `depends_on = None`

In `upgrade()`:
1. Create `users` table: user_id (String(36) PK), email (String(255) UNIQUE INDEX), hashed_password (String(255)), created_at (TIMESTAMP server_default=func.now())
2. Create `teams` table: team_id (String(36) PK), name (String(255)), owner_id (String(36) FK->users.user_id), created_at (TIMESTAMP server_default=func.now())
3. Create `team_members` table: team_id (String(36) FK->teams.team_id PK), user_id (String(36) FK->users.user_id PK), role (String(32) default="member"), joined_at (TIMESTAMP server_default=func.now())
4. Create `nodes` table: node_id (String(255) PK), platform (String(64)), version (String(32)), projects (JSON nullable), team_id (String(36) FK->teams.team_id nullable), status (SAEnum NodeStatus default="disconnected"), first_seen (TIMESTAMP server_default=func.now()), connected_at (TIMESTAMP nullable), last_heartbeat (TIMESTAMP nullable), last_seen (TIMESTAMP nullable)
5. Create `instances` table: instance_id (String(36) PK), node_id (String(255) FK->nodes.node_id), project (String(255)), prompt (Text nullable), session_id (String(255) nullable), status (SAEnum InstanceStatus default="pending"), exit_code (Integer nullable), error (String(2048) nullable), started_at (TIMESTAMP nullable), finished_at (TIMESTAMP nullable), created_at (TIMESTAMP server_default=func.now())
6. Create `audit_log` table: id (Integer PK autoincrement), timestamp (TIMESTAMP server_default=func.now() INDEX), node_id (String(255) nullable INDEX), instance_id (String(36) nullable), user_id (String(36) nullable), event_type (String(64)), details (JSON nullable)

Use `sa.Enum("connected", "stale", "disconnected", name="node_status")` and `sa.Enum("pending", "running", "finished", "errored", name="instance_status")` for the enum columns.

In `downgrade()`: drop tables in reverse order (audit_log, instances, nodes, team_members, teams, users), then drop enums.
